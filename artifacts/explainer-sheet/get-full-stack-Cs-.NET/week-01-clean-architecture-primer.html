Clean Architecture Primer

Week 1 was a tour of one .NET service. The tour isn't the lesson. What transfers to any backend is four questions you learn to ask: where are the boundaries, which way do dependencies point, how long do things live, and how does a service say no?

Week 1 goal Name every box in the system and say who owns it · run the service locally with a green health check · be able to say which layer a change belongs in.
Start here

A server is not a browser

Everything else follows from this

One tab and one user, versus one process and hundreds of users at once. Every difference in this document comes from that.

  • Shared state becomes a hazard, not a convenience. This is the reason lifetimes exist later in this document.
  • Nothing is disposable. The process outlives the request, so anything kept in memory persists — and vanishes on restart. If a service keeps sessions in memory on a single instance, that is exactly why a restart logs everybody out.
  • async/await looks identical but isn't. Same keywords; work runs on thread-pool threads rather than one event loop. The parallelism is real, so the concurrency bugs are real.
  • There's a compile step. No Vite-style hot reload. Hot reload exists within limits; some edits demand a restart.
→So the first question is: what's actually inside that process that we control?
First, the words

How objects work here

Needed for everything after this

Five words that the rest of this document leans on. In React you rarely think about object creation; here it's the whole mechanism.

class

A blueprint. class User { } describes the shape of a thing. Same as TypeScript.

instance

One actual object built from the blueprint. new User() makes one, with its own values inside it. Two instances are two separate objects that share nothing. Every lifetime question later is only ever: how many of these exist, and who shares them?

constructor

The method that runs when an instance is created, and where a class receives the things it needs to do its job. This is the hook dependency injection plugs into.

property

public string Email { get; set; } — looks like a plain field, but is really a pair of tiny methods. Week 5 previewthis is why the database layer can notice when a value changes.

interface

A promise about what something can do, with no code for how. IUserRepository says "there is a way to get a user by email" without saying where the data comes from. A leading I always means interface. This is the keystone of the whole architecture — it comes back under “The inversion”.

One real divergence from TypeScript. In TS, any object with a matching shape satisfies an interface. In C# a class must explicitly declare that it implements one — class UserRepository : IUserRepository. Matching by accident isn't enough, and that single rule explains most of the extra ceremony you're about to see.

→Now the words exist. Next: which pieces of this system are ours to change?

The four projects

The inner boundary

One service splits into four projects, each compiled separately. The names are unhelpful at first, so here is what each one actually holds, with indicative file counts.

≈ your api-client layer

Two of these names actively mislead — worth saying out loud.

"Application" sounds like it means the whole app. It doesn't; it's only the rules. Program.cs, the file that actually starts the application, lives in Api.

"Domain" sounds technical. It isn't. It means the business's own vocabulary — the words a salesperson would use. User, plan, subscription, lead.

What the classes are called

How to navigate the file tree

The words on every diagram from here — Controller, Service, Repository — are job titles. Here's the job each one does.

Controller

The class that receives HTTP requests. One class per area of the API, one method per endpoint — PlansController.GetPlans() runs when the UI hits GET /plans. ≈ your route handler.

Service

A class holding the rules for one area of work. Controllers call them; they call repositories and clients. The name just means a class that does work, named after the work.

Repository

A class whose only job is getting things in and out of the database. Roughly one per entity, and nothing else in the app touches the database directly. ≈ the one module in your app allowed to call fetch.

Client
Provider

A class whose only job is talking to one external system — StripeApiClient, Auth0Client. Same idea as a repository, but over HTTP. Provider is this repo's word for the ones that send something out: SendGridEmailProvider, TwilioSmsProvider.

A heuristic, not a law. Real repositories always have exceptions — a class ending Service sitting in a clients folder, or an XService in Application alongside an XClient in Infrastructure. When the suffix and the folder disagree, the folder is the truth.

→Now you know the pieces and their names. What are they allowed to do to each other?
02

Direction — which way do dependencies point?

Model two of four

Each project declares which others it is allowed to use. Those declarations are the architecture — not the folder names.

This shape is not universal. Plenty of services have no Domain or Application project at all — they split by technical role instead, or carry older projects alongside newer ones from a half-finished migration. Don't assume the four names exist before you look. The last sheet contrasts the two shapes.

The one shape that can't exist

Circular dependency

Why it's impossible rather than discouraged. Each project compiles into its own separate file, and to compile one the compiler needs the finished output of everything it uses. To build A it needs B finished; to build B it needs C finished; to build C it needs A — which hasn't started. There's no order in which the build can happen.

Two different things protect you, and they're worth telling apart. The compiler makes a circular dependency impossible — it cannot produce output. Separately, Rider is being helpful: when you open the Add Reference dialog, choices that would create one are simply not offered.

You have hit this before — silently. TypeScript compiles everything into one bundle, so circular imports between files are legal there. You don't get a build error; you get the mystery bug where an import is undefined at runtime in whichever file happened to load second. Here the same shape can't get past the build.

→The arrows say who may use whom. But Domain is allowed to use nothing — so how does it ever reach Stripe?
02

The inversion

The keystone · spend time here

Two arrows run between the same two boxes, in opposite directions. Data flows outward to Stripe. The permission to use still points inward.

Payoff one — you can work in Application without learning Stripe. Open PaymentService.cs and the only Stripe-shaped thing in it is the name IStripeApiClient. No SDK, no API keys, no webhook semantics. The entire Stripe surface stays out of your head while you change the rules.

Payoff two — tests don't need the internet. PaymentService holds an interface, so a test hands it a stand-in that returns whatever the test wants. No test ever calls Stripe. You can only do this because the interface exists.

Worth knowing before you trust the picture. In practice the innermost project is rarely sealed off. It commonly references third-party SDKs and the database library, and an interface declared there may take and return vendor types. The shape above is real and worth learning; the purity it implies rarely survives contact with a shipping product.

→These arrows say who may use whom. But somebody has to actually build these objects — who, and when?
03

Who builds these objects?

Model three of four · first, the container

Before lifetimes can mean anything, two things have to be on the table: what a request is, and who is doing the building.

a request

One HTTP call, with a beginning and an end. The framework opens a fresh workspace when it arrives and closes it when the response goes out. That window is what "per request" means below.

Constructor injection is props for classes. A React component doesn't create its own props — the parent passes them in. That's exactly why you can test a component by passing fake props. Same mechanism here: a class lists what it needs in its constructor, and something above it supplies them.

That something is the container. It has two halves, and they live in different files:

Once, in Program.cs — what to use:

AddScoped<IUserRepository, UserRepository>();
AddScoped<IPaymentService, PaymentService>();

Everywhere else — what you need:

public PlansController(
    IPaymentService paymentService)
// never new PaymentService(...)
→So the objects get built for you. The remaining question is how long each one sticks around.
03

Lifetime — how long does this thing live?

Build fresh, or hand over one you have?

A direct consequence of one process serving many users at once.

So the question a lifetime answers is just this: when something asks the container for an IUserRepository, should it build a fresh one, or hand over one it already built? There are three possible answers, and that's all a lifetime is.

Registered asWhat the container does when askedUsed here for
TransientAlways builds a fresh one. Ask twice, get two separate objects.cheap, short-lived objects
ScopedBuilds one per request, then reuses that same one for the rest of that request. Next request gets a new one.anything holding a database workspace or per-user state
SingletonBuilds one the first time it's ever needed, then hands that same object to every request forever — until the app restarts.stateless helpers, caches, API clients

The part that makes "Scoped" click. "One per request" hides the point. During a single request, several different services each ask the container for IUserRepository — and they all get the same one. That sharing is the value: one request gets one workspace, so everything that happens during it belongs to the same piece of work. It is not "a new one every time"; that's Transient.

→So why does it matter which one you pick? Because of what some of these objects are holding.
03

Why the choice matters

What goes wrong when the lifetime is wrong

Why this sheet exists: a lifetime looks like a performance setting — how often do we rebuild this thing? It isn't. It's a correctness decision. Pick wrong and you write the wrong data to the database. Here is the object that makes it so, and the two ways people get there.

Week 5 previewA DbContext is a workspace, not a connection. Load a user through it and it keeps a copy and watches it. Change a property and it records "email changed". Call SaveChangesAsync() and it writes every change it has recorded, all at once.

That one fact — it holds unsaved work in progress — is what makes sharing one between requests dangerous.

Two ways to end up there

Both mistakes have the same destination — one DbContext shared by every request, exactly as drawn above. They just take different routes.

Route A — register it Singleton. The obvious one. One repository object for the whole process, so one workspace for every request that ever arrives.

Route B — register it Scoped, then inject it into a Singleton. The subtle one. The registration is right, but a singleton grabs one instance and never lets go.

Route B is the stale closure, and you've had this bug in React. A long-lived thing captures a snapshot of a short-lived thing and freezes it — a callback still confidently using a value from three renders ago. Same shape, three steps:

  • A singleton is built once, so its constructor runs once.
  • Whatever the container puts into that constructor is what the singleton keeps — forever.
  • If one of those things was scoped, a per-request object is now permanent, shared by every request that ever arrives.

The rule that prevents both. A singleton must never hold a scoped dependency. The other direction is safe: a scoped thing may depend on a singleton. If someone calls this a "captive dependency", this is what they mean.

Good news you'd otherwise learn the hard way. In the Development environment, .NET refuses to start and tells you — it validates that no singleton is consuming a scoped service. In other environments that validation is off, so the app starts fine and quietly misbehaves. So you'll usually meet this as a startup error while you're working, not as a production mystery.

→Objects now exist and can do work. What happens when the work fails?
04

Failure — how does a service say no?

Model four of four

First, what "the stack" means. When Controller calls Service calls Repository, each one is sitting there waiting on the next. That's the stack. If the repository throws, it stops, then the service stops, then the controller stops — all the way up until something catches it. Nobody in between gets a say. That's what "unwinding" means.

A service says no the same way useQuery says no — it hands back { data, error } and makes you look. Throwing instead is like letting a fetch blow up into an error boundary: technically it's handled, but nobody in between got to choose what the user sees.

What you already write:

const { data, error } = useQuery(...)
if (error) return <Message/>
// now data is safe to use

The same move here:

var result = await _service.GetPlansAsync(id);
if (result.IsError) return ...;
// now result.Data is safe to use

Result<T> is { data, error }. Same shape, same discipline: the thing that can fail hands back a wrapper, and you check the error before you're allowed to trust the data.

// can this fail? nothing in the signature tells you
Task<User>         GetUserAsync(string email);

// failure is part of the return type — the caller must look
Task<Result<User>> GetUserAsync(string email);

A throw is invisible in the signature. The caller has no way to know it's coming, so it can't be made to handle it. Result<T> puts failure in the return type, so the compiler makes you check.

04

The same two choices, in C#

Then: who picks the number?

Heads up — a codebase can easily hold two different Result<T> types. A hand-rolled one with IsError / Data / Error, and a library one from a package such as LanguageExt, which you consume with .Match(Succ:, Fail:) instead. A service sitting between them converts from one to the other. Two Result APIs one file apart is a normal thing to meet; you're not going mad.

Who decides the status code?

The service does, not the controller

The service picks a ReturnStatus when it builds the failure. The controller's ToActionResult only translates it. This is the lookup table.

The two that will trip you up. Validation failures here return 422, not the 400 you'd expect. And a successful result whose Data is null returns 204 No Content, not 200 with an empty body. Both are decided in a single switch in whichever extension method maps results to responses.

Expected or unexpected? A test you can actually apply

The convention is that expected failures are returned and unexpected ones are thrown. The way to tell them apart:

Would you write a test asserting this outcome?

Yes → return it. It's a normal outcome of a working system. User not found. Email already taken. Session expired. Card declined.

No → let it throw. Nobody planned for it and there's nothing sensible to return. Database unreachable. A bug. A null that shouldn't be possible.

Throwing for an expected outcome is slow and hides intent — and as the signature comparison showed, it takes the decision away from every caller in between.

There is no scripts block. restore, build, run, test and publish are built-in dotnet verbs fixed by the SDK — not aliases someone defined in the project file. You can't invent dotnet dev.

Three bits of C# syntax you met in passing. [Attributes] in square brackets are metadata the framework reads and acts on — [Route], [HttpGet], [FromHeader], [Authorize]. Extension methods are a static method whose first parameter is this ISomething x, which makes it appear on every ISomething — that's why AddSwaggerGen() and ToActionResult() read like built-ins. Anonymous objects — new { status = "healthy" } — are a plain object literal with no declared class, which is what the health endpoint returns.

Two ways to split a service

Clean architecture vs MVC

Clean architecture is the model this whole document teaches. It isn't the only one you'll meet — and the contrast is the fastest way to see what it's actually buying.

The practical rule when you land in an unfamiliar service. Find out which shape you're in before you write anything — count the projects and read one .csproj. Then follow the local convention, not the one you learned first. A service organised by technical role isn't waiting to be rescued, and a half-finished migration between the two is the most common thing you'll actually meet.
